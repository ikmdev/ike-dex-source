description: Ingest source documents for one device (GUDID record, 510(k) decision summary, package insert or IFU, other PDF or Word files) into the topic library and create the device's folder under devices/. Use when asked to ingest, import, convert or decompose a source document.

Ingest the source documents named in the arguments (`$ARGUMENTS`; ask for their paths if none were given) for one device into this repo: topics in `sources/topics`, then the device's folder under `devices/`. The worked example is device 07332940008581 (Cepheid Xpert Xpress CoV-2 plus): its topics and its module under `devices/`. DeX records, manifests and changesets come later; do not create them.

**Read first.** `CLAUDE.md`, `README.md` and `devices/README.md` (the source of truth). Get the IKE standards as the README's Setup describes, then read IKE-INGEST, IKE-TOPIC-DECOMPOSITION, IKE-ASCIIDOC-FRAGMENT, IKE-TOPIC-REGISTRY, IKE-ASSEMBLY and IKE-INDEX. IKE-DEX-INGEST is not unpacked: read it from IKE-Network/ike-tooling.

**Classify, gather provenance and confirm once, before converting.** Keep the reading cheap: read only the cover or first page, the last page, the running headers and footers (the page furniture) and the file's own metadata, and search the text layer for copyright, trademark, license, revision and identifier wording rather than loading the whole document (use page images only where there is no text layer). Run the 510(k) gate (README, Ingest step 1) on the first page. Classify each source. For a third-party source, which may be copyrighted, ask the IKE-INGEST confirmation (type, handling (decomposed, whole document, summary), quotation, `:topic-license:`) and the provenance validation below together, in one round of `AskUserQuestion` calls (see below), so the user answers once. Show the notice you found next to the handling and license choices, since it informs them. Never reproduce copyrighted text without the user's explicit decision. If conversion later shows a notice that conflicts with what was confirmed, stop and ask again before placing topics.

**Provenance (every external source).** Establish these five items for each source from the parts of the document named above (cover, legal and copyright notices, footers, file metadata) and, where relevant, the publisher's site. Never infer them from the document type: a 510(k), a GUDID record or a label does not by itself tell you the originating party, copyright status or license terms. Ask the user to validate what you found, as described below, in the same round as the IKE-INGEST confirmation, and wait for the answers before converting. The findings go in three header attributes, worded from the document:

| Item | What to establish | Header |
| --- | --- | --- |
| Originating party | Who authored or published the document, as the document names them (manufacturer, agency, standards body). Past examples are only suggestions to check against the document, each with the document type it came from: `U.S. Food and Drug Administration and U.S. National Library of Medicine` (GUDID record), `U.S. Food and Drug Administration, Center for Devices and Radiological Health` (510(k) decision summary), `Cepheid` (manufacturer labeling). For a 510(k), also note the applicant. | Opening words of `:topic-citation:` |
| Source identifier and URL | The canonical identifier (GUDID DI, 510(k) K-number, PMA P-number, De Novo DEN-number, SPL setid, openFDA record id) and the URL of the original document, such as its PDF on the publisher's site. Look in the document, in the file's metadata (such as where it was downloaded from) and on the publisher's site. If you cannot find the original document's URL, ask the user for it. | `:topic-citation:`: identifier in the title, URL last |
| Retrieval date | Offer options and let the user choose: today's date; the date the file was added or downloaded (from its metadata or timestamp); or a date they supply. | `:topic-citation:`: `Accessed {Month D, YYYY}.` or `Retrieved {Month D, YYYY}.` |
| Version or document identifier | As printed: edition, revision and date, document or catalog number, 510(k) template, GUDID public version number and date. | `:topic-citation:` |
| Asserted copyright status | What the document itself asserts: find its copyright, trademark or legal notice and quote or closely paraphrase it. If it asserts nothing, write that nothing is stated and ask the user; do not assume a status from the document type. Where the notice matches an IKE-INGEST `:topic-license:` value, use that wording. | First words of `:topic-license:`; trademark claims in `:topic-notes:` |
| License terms, where stated | Any redistribution or use terms the document or its source site states, quoted or closely paraphrased. If none are stated, say so in `:topic-notes:`. If the document restricts use, note that reuse beyond those terms needs the holder's permission, and note anything odd, such as a file name that differs from the stated revision. | Rest of `:topic-license:`; absence in `:topic-notes:` |

The DeX manifest written later lists these same fields per source (Originating Party, Source URL or Canonical Identifier, Retrieval Date, Version or Document Identifier, Asserted Copyright Status, License Terms), so keep the wording exact.

**Asking for validation.** Ask with the `AskUserQuestion` tool, which needs an answer before you continue. Do not print the findings as a markdown message, table or paragraph first. The tool takes at most four questions per call, each with two to four options (the user can always type another answer), so work one source at a time in two calls:
1. Identity: originating party, source identifier and URL, version or document identifier, retrieval date.
2. Rights and handling: copyright status, license terms, handling (decomposed, whole document, summary) and quotation approach.

For each question:
- Use the item name as the short header (`Party`, `Source URL`, `Version`, `Retrieved`, `Copyright`, `License`, `Handling`, `Quotation`) and ask the question in a full sentence.
- Make the first option your proposed value, marked `(Recommended)`, with the evidence in its description (page or section, and the quoted text). Prefer what the document explicitly states over anything you inferred, however plausible. Add the other candidates you found, inferred ones included, as further options.
- Keep labels short and put long values (URLs, quoted notices, citations) in the description.
- Offer the retrieval-date options named above. When you could not find something, such as the original URL or a license statement, make the options say so (for example "Not stated in the document") and let the user type the real value.

The answers, with any corrections, are what you write into the headers.

**Converter prerequisite.** Check that `../ike-dex-docs` exists (a sibling of this repo) and has `utilities/.venv/bin/python`. If not, stop and warn the user: from this repo's parent directory run `git clone https://github.com/ikmdev/ike-dex-docs.git`, install Pandoc, then run `./utilities/setup.sh` inside it. Do not clone or install it yourself.

**Convert and verify.** `../ike-dex-docs/utilities/.venv/bin/python ../ike-dex-docs/utilities/document_to_asciidoc.py <src> -o sources/work/raw/<name>.adoc` (`work/` is gitignored). For a PDF, run `check_fidelity.py` from the same folder with the same Python: also compare page images, since it trusts the PDF's tags. Never hand-edit the converted content, now or later. List what was not converted correctly (failing fidelity gates, differences in the page images, tables, lists, headings or pictures, the converter's own `// Check` and `// REVIEW` comments) and ask the user, with `AskUserQuestion`, which if any they want fixed; change only what they name. Default to not fixing: make "Leave as converted" the first option, marked `(Recommended)`, for every item, including the fixes you could propose. The reason is determinism: the converter gives the same output every time from the same source, so anyone can reproduce the topics by re-running it, while a hand fix cannot be reproduced and is lost or silently reverted the next time the document is converted. State this reason in the question, name the item and what the fix would change, and offer "Fix it" only as an alternative. Record every item left unfixed under deviations in the final report. Adding the topic header, anchor and index terms, removing document-level attributes and placing images are what the standards require, not edits to the converted text.

**Normalize early and often.** From `sources/`: `mvn -B -N slb:reformat "-Dfile=work/raw/<name>.adoc"` (`-DdryRun=true` first). Run it right after conversion, after the header and index terms are added, and on the placed file. Compare words, ignoring whitespace, before and after each run. A last dry run must report 0 changes.

**Topics** (`sources/topics/src/docs/asciidoc/`). Place under `topics/ext/{type}/`, `topics/gudid/` or `topics/dex/` (whole-document `gudid-{DI}` and `dex-k######` records). Header per IKE-ASCIIDOC-FRAGMENT with the provenance above, `ext-` ids for external sources, status at most `review`, no document-level attributes, images in `images/{domain}/{doc-slug}/` relative to imagesdir. Add 3-10 `indexterm:[…]` (5-15 for DeX records). Add each topic to `index.adoc`, non-`ext/` topics to `assemblies/compendium`, and `:topic-related:` ids both ways. `mvn -B idoc:topic-registry -pl topics` (from `sources/`) must report `0 findings`.

**Device folder.** From the GUDID record take the Primary DI, GMDN term and device type. Copy `devices/_template/` (omit its DeX record skeleton) to `devices/{device-group}/{category}/{gmdn-term-slug}/{primary-DI}/`: `IVDs` for in-vitro diagnostics; for other device types follow `devices/README.md` and ask the user which group folder to use. Rename `pom.xml.template` and fill the placeholders. Add one assembly file per ingested document in `src/docs/asciidoc/`, named like the topic file it includes (e.g. `GUDIDRecord_{DI}.adoc`, `{slug}-ifu.adoc`). Keep every assembly directly in `src/docs/asciidoc/`: do not create a subfolder for an IFU or any other document, and write the DeX record's `:src-*:` values as bare file names. Each assembly has device metadata and `include::…[leveloffset=+1]` (`ext/` allowed). Leave `pdf.source.document` as the template sets it, and do not add the device to `devices/pom.xml` yet: both wait until the DeX record exists.

**Done means** root `mvn clean verify` succeeds with no unresolved include, missing image or invalid-reference warning (when Prince is installed, add `-Dike.skip.prince=false` to this same build so it runs once, confirm each built module's `target/generated-docs/pdf-prince/` holds its PDFs and summarize the logs as below; if Prince is not installed, say the PDF was not built); registry `0 findings`; every topic header carries all five provenance items, confirmed by the user; every `include::` in the device's assemblies points at an existing topic; no source content lost.

**Prince log summary.** Each Prince log (`target/logs/renderer-prince*.log`) holds hundreds of lines per build, mostly repeats of a few kinds. Do not list or fix them. Group the lines by kind (ignore file names, line and page numbers), count each kind, and give the user a verdict line followed by a short table: Kind | Count | What it means for the PDF | Action needed? Use plain language. Kinds seen so far:
- table header cell has no associated subcells; possibly inappropriate use of P structure element; not identifying as PDF/UA: the PDF's accessibility tagging (screen-reader structure) is imperfect, so it cannot claim PDF/UA conformance. Nothing changes visually.
- SSL certificate error fetching web fonts or icon styles: the PDF uses default fonts and icons. This is a machine or network matter, not a content one.
- no font for a Private Use Area character: an icon glyph is replaced by a placeholder.
- unsupported CSS properties: ignored, no visible effect.
- can't open input file: an image or stylesheet was not found, so figures or styling are missing from that PDF. This is the only kind that affects content; name the files.

If a kind is not listed, say what the message appears to mean and that it is unrecognized. The verdict line says whether the PDFs built and whether anything affects their content.
